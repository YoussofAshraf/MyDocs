🤔 Why a Message Broker?

  Synchronous (tight coupling) 😰           Asynchronous via broker 😌  ───────────────────────────────           ──────────────────────────────────  Order API ──HTTP──▶ Email svc  ⏳          Order API ──▶ 🐇 ──▶ Email svc            ──HTTP──▶ Invoice svc ⏳                        ├──▶ Invoice svc            ──HTTP──▶ Stock svc   💥 down                   └──▶ Stock svc (down? msgs wait 📥)   • slowest service sets latency            • API replies instantly  • one failure fails the request           • failures isolated, retried later  • spikes overload everyone                • queue absorbs spikes (load leveling)

Benefit Meaning
Decoupling Producers don't know who consumes, or how many consumers there are
Buffering Queues absorb bursts, and consumers work at their own pace
Reliability Persisted messages + acks survive crashes
Scalability Add consumers to process in parallel (competing consumers)
Routing Deliver to the right services with flexible rules

🏛️ Broker Architecture

👀 Boxes light up as the flow reaches them and each arrow draws in the order the guide defines it. Glowing dots keep running along the arrows to show which way things move.

Concept What it is
Broker / node A RabbitMQ server (Erlang VM). Several nodes form a cluster
Virtual host (vhost) Logical namespace with its own exchanges, queues and permissions (like a DB schema)
Connection Long-lived TCP (optionally TLS) connection from an app
Channel Lightweight virtual connection multiplexed inside one TCP connection
Exchange Receives published messages and routes them
Queue Ordered (FIFO) buffer that stores messages for consumers
Binding Rule linking an exchange to a queue (or to another exchange)
Routing key Label on a message that the exchange matches against bindings

Step by step

  1. exchange: orders → queue: email binding
  2. exchange: orders → queue: invoice binding
  3. publisher → exchange: orders TCP connection → channel
  4. queue: email → consumer
  5. queue: invoice → consumer

🔌 Connections vs Channels

  App process  ┌──────────────────────────────────────────────────┐  │  thread A ── channel 1 ─┐                        │  │  thread B ── channel 2 ─┼══ ONE TCP connection ══╪══▶ 🐇  │  thread C ── channel 3 ─┘   (TLS, heartbeats)    │  └──────────────────────────────────────────────────┘

👀 The drawing is revealed line by line. Arrows pulse, and ✅ / ❌ marks pop in to show the verdicts.

  • ✅ One connection per process, with one channel per thread or task.
  • ❌ Don't open a connection per message: it's expensive (TCP + TLS + AMQP handshake).
  • ⚠️ Channels aren't thread-safe in most clients, so don't share one channel across threads.
  • 💡 Use separate connections for publishing and consuming, so flow control on publishers doesn't stall consumers.

🔁 The Basic Flow

👀 Read it top to bottom: each message is sent in turn, and a dot travels from the sender to the receiver. Dashed lines are replies.

Step by step

  1. Producer → Exchange: basic.publish (routing key)
  2. Exchange → Queue: route via bindings
  3. Queue ⇠ Producer: publisher confirm ✅ (if enabled)
  4. Queue → Consumer: basic.deliver (up to prefetch limit)
  5. Consumer → Consumer: process
  6. Consumer → Queue: basic.ack ✅ → message deleted
  7. 📝 Consumer, Queue: nack / reject → requeue or dead-letter
