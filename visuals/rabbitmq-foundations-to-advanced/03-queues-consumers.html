💾 Durability: Three Things Must Line Up

Queue property Meaning
durable Definition survives a broker restart
exclusive Belongs to one connection, deleted when it closes (temp reply queues)
auto-delete Deleted when the last consumer leaves
x-max-length / x-max-length-bytes Cap size; x-overflow: drop-head (default) or reject-publish
x-message-ttl Messages expire after N ms
x-dead-letter-exchange Where rejected or expired messages go (ch. 04)
State machine · 2/7

✅ Consumer Acknowledgements

👀 States appear one after another and each transition draws in order. ● is the start and ◉ is the end.

Mode Behavior Risk
auto-ack (auto_ack=True) Considered done as soon as it is sent ❌ Lost if the consumer crashes mid-processing
manual ack ✅ You ack after processing succeeds Duplicates possible after a crash, so be idempotent

Step by step

  1. ● → Ready enqueued
  2. Ready → Unacked delivered to consumer
  3. Unacked → ◉ basic.ack ✅ deleted
  4. Unacked → Ready basic.nack(requeue=true) 🔁 or consumer/channel died
  5. Unacked → DeadLettered basic.reject / nack(requeue=false) ☠️
  6. DeadLettered → ◉

⚖️ Competing Consumers (Work Queue)

👀 Boxes light up as the flow reaches them and each arrow draws in the order the guide defines it. Glowing dots keep running along the arrows to show which way things move.

  • Messages go round-robin among consumers, limited by prefetch.
  • Scale throughput by adding consumers.
  • Ordering is only guaranteed per queue with a single consumer. Use x-single-active-consumer if you need one active consumer with hot standbys.

Step by step

  2. queue: thumbnails → worker 1 msg 1, 4, 7
  3. queue: thumbnails → worker 2 msg 2, 5, 8
  4. queue: thumbnails → worker 3 msg 3, 6, 9

📮 Publisher Confirms: Reliability on the Publish Side

👀 Read it top to bottom: each message is sent in turn, and a dot travels from the sender to the receiver. Dashed lines are replies.

Step by step

  1. Publisher → Broker: confirm.select (enable once per channel)
  2. Publisher → Broker: publish #1, #2, #3 (async, batched)
  3. Broker ⇠ Publisher: ack #1..#2 ✅ (persisted / replicated)
  4. Broker ⇠ Publisher: nack #3 ❌ → republish
  5. 📝 Publisher: track outstanding seq numbers, retry on nack or timeout

  Without confirms: publish() returns → message could still be lost 🕳️  With confirms:    broker ack = it's safely in the queue(s) ✅

👀 The drawing is revealed line by line. Arrows pulse, and ✅ / ❌ marks pop in to show the verdicts.

💡 For quorum queues, the confirm arrives once a majority of replicas have written the message. Publish asynchronously and handle confirms in batches for throughput.
