☠️ Dead Letter Exchanges (DLX)

👀 Boxes light up as the flow reaches them and each arrow draws in the order the guide defines it. Glowing dots keep running along the arrows to show which way things move.

A message is dead-lettered when it is:

  1. rejected or nacked with requeue=false
  2. expired (TTL)
  3. dropped because the queue is full (x-max-length)
  4. over the quorum queue delivery limit (default 20 in RabbitMQ 4.x)

Step by step

  1. Producer → orders
  2. orders → orders.q x-dead-letter-exchange: dlx
  3. orders.q x-dead-letter-exchange: dlx → Consumer
  4. Consumer ⇢ orders.q x-dead-letter-exchange: dlx nack requeue=false
  5. orders.q x-dead-letter-exchange: dlx → dlx dead-letter
  6. dlx → orders.dlq
  7. orders.dlq → 👀 alert / inspect / replay

🔁 Retry with Backoff (Delay Queues)

👀 Boxes light up as the flow reaches them and each arrow draws in the order the guide defines it. Glowing dots keep running along the arrows to show which way things move.

Don't requeue instantly in a hot loop. Park failures in a wait queue whose TTL sends them back.

Step by step

  1. work.q → Consumer
  2. Consumer → retry.5s TTL 5s DLX → work fail, retry < 3 publish to retry
  3. retry.5s TTL 5s DLX → work → work.q expires
  4. Consumer → retry.30s TTL 30s DLX → work fail again
  5. retry.30s TTL 30s DLX → work → work.q expires
  6. Consumer → work.dlq ☠️ retries exhausted

🔁 Retry with Backoff (Delay Queues)

  attempt 1 ❌ → wait 5s → attempt 2 ❌ → wait 30s → attempt 3 ❌ → parking lot (DLQ)  track attempts in a header: x-retry-count (or read x-death)

👀 The drawing is revealed line by line. Arrows pulse, and ✅ / ❌ marks pop in to show the verdicts.

Delay option Notes
TTL + DLX queues (above) No plugin needed. One queue per delay tier
rabbitmq_delayed_message_exchange plugin x-delay header per message. Not replicated, so avoid it for critical data at scale
Scheduler outside the broker DB or cron for long delays (hours or days)

⚠️ In classic queues, per-message TTL is only applied at the head of the queue, so expired messages behind live ones wait their turn.

📞 RPC (Request / Reply)

👀 Read it top to bottom: each message is sent in turn, and a dot travels from the sender to the receiver. Dashed lines are replies.

💡 Use Direct Reply-to (amq.rabbitmq.reply-to) so you don't create a reply queue per request. Always set a client-side timeout.

Step by step

  1. Client → Broker: publish to rpc.q reply_to=amq.rabbitmq.reply-to correlation_id=abc
  2. Broker → Server: deliver request
  3. Server → Broker: publish result to reply_to correlation_id=abc
  4. Broker → Client: deliver reply → match correlation_id ✅

At-least-once delivery means duplicates will happen (redelivery after a crash, publisher retries).

Other tools: natural idempotency (SET status='paid' rather than balance += 10) and upserts.

📤 Transactional Outbox (Publishing Reliably from a DB)

👀 Boxes light up as the flow reaches them and each arrow draws in the order the guide defines it. Glowing dots keep running along the arrows to show which way things move.

The problem: "save the order, then publish" can fail halfway, so you get an order with no event, or an event with no order.

Step by step

  1. Order API → orders + outbox table single DB TX
  2. Outbox relay poller or CDC/Debezium → orders + outbox table read unsent
  3. Outbox relay poller or CDC/Debezium → 🐇 exchange publish + confirm
  4. Outbox relay poller or CDC/Debezium → orders + outbox table mark sent
