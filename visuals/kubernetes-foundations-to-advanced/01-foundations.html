Step by step

  1. 👤 kubectl / CI / GitOps → kube-apiserver front door HTTPS REST
  2. kube-apiserver front door → etcd key-value store
  3. kube-scheduler picks nodes → kube-apiserver front door
  4. controller-manager reconcile loops → kube-apiserver front door
  5. cloud-controller-manager LBs, disks, nodes → kube-apiserver front door
  6. kubelet → container runtime containerd / CRI-O
  7. container runtime containerd / CRI-O → Pod
  8. container runtime containerd / CRI-O → Pod
  9. kubelet → container runtime
  10. container runtime → Pod
  11. kube-apiserver front door → kubelet
  12. kube-apiserver front door → kubelet

🔁 The Reconciliation Loop

👀 Boxes light up as the flow reaches them and each arrow draws in the order the guide defines it. Glowing dots keep running along the arrows to show which way things move.

Every controller runs the same loop:

Example: you ask for replicas: 3. A node dies and takes one Pod with it. The ReplicaSet controller sees 2 ≠ 3 and creates a new Pod. Nobody gets paged.

Step by step

  1. Observe actual state → Diff with desired state
  2. Diff with desired state → Observe actual state match
  3. Diff with desired state → Act create / delete / update drift
  4. Act create / delete / update → Observe actual state

🚶 What Happens on kubectl apply?

👀 Read it top to bottom: each message is sent in turn, and a dot travels from the sender to the receiver. Dashed lines are replies.

💡 Components never talk directly to each other. They all watch the API server. This loose coupling is what makes Kubernetes extensible.

Step by step

  1. kubectl → API Server: POST Deployment (YAML)
  2. API Server → API Server: AuthN → AuthZ → Admission
  3. API Server → etcd: persist Deployment
  4. Deployment Ctrl → API Server: watch: new Deployment
  5. Deployment Ctrl → API Server: create ReplicaSet → Pods (Pending)
  6. Scheduler → API Server: watch: unscheduled Pods
  7. Scheduler → API Server: bind Pod → node-2
  8. kubelet (node) → API Server: watch: Pod bound to me
  9. kubelet (node) → kubelet (node): pull image, start containers
  10. kubelet (node) → API Server: status: Running ✅

🏷️ Namespaces, Labels & Selectors

Cluster├── namespace: kube-system   (K8s internals)├── namespace: default├── namespace: shop-dev│     ├── Deployment web   labels: app=web, env=dev│     └── Deployment api   labels: app=api, env=dev└── namespace: shop-prod      ├── Deployment web   labels: app=web, env=prod      └── Deployment api   labels: app=api, env=prod

👀 The drawing is revealed line by line. Arrows pulse, and ✅ / ❌ marks pop in to show the verdicts.

  • Namespaces give names a scope and are where quotas and RBAC apply. They are not a hard security boundary by themselves.
  • Labels are key/value tags. Selectors query them: kubectl get pods -l app=web,env=prod.
  • Annotations hold non-identifying metadata (build info, tool config).
