🔁 Replication

👀 Boxes light up as the flow reaches them and each arrow draws in the order the guide defines it. Glowing dots keep running along the arrows to show which way things move.

Term Meaning
Replication factor (RF) Copies of each partition (production: 3)
Leader Handles all writes (and reads by default)
Followers Fetch from the leader to stay in sync
ISR (in-sync replicas) Replicas that caught up within replica.lag.time.max.ms
High watermark (HW) Highest offset replicated to all ISR. Consumers only see up to the HW
ELR (eligible leader replicas, newer KRaft feature) Tracks replicas safe to elect even after shrinking the ISR

Step by step

  1. Producer → orders-0 👑 LEADER write
  2. orders-0 follower ✅ in-sync → orders-0 👑 LEADER fetch
  3. orders-0 follower ⏳ lagging → out of ISR → orders-0 👑 LEADER fetch

🛡️ The Durability Triangle

           replication.factor = 3                    ▲                   ╱ ╲                  ╱   ╲   acks = all ───╱─────╲─── min.insync.replicas = 2  → a write is acked only when ≥ 2 replicas have it → tolerates losing 1 broker with NO data loss and writes still accepted → if ISR drops below 2 → producers get NotEnoughReplicas (safe failure, not silent loss)

👀 The drawing is revealed line by line. Arrows pulse, and ✅ / ❌ marks pop in to show the verdicts.

RF min.insync Survive broker loss for writes Data-loss safety
1 1 ❌ ❌
3 1 2 brokers ⚠️ weak (one copy acked)
3 2 ⭐ 1 broker ✅
3 3 0 ✅ but fragile

⚠️ Keep unclean.leader.election.enable=false (default). Turning it on lets an out-of-sync replica become leader: you get availability at the cost of data loss.

👑 Leader Election & Rack Awareness

👀 Read it top to bottom: each message is sent in turn, and a dot travels from the sender to the receiver. Dashed lines are replies.

  • broker.rack=az-1|az-2|az-3 spreads replicas across availability zones.
  • client.rack + follower fetching lets consumers read from the nearest replica (saves cross-AZ costs).

Step by step

  1. 📝 broker 1 (leader): 💥 broker 1 fails
  2. KRaft controller → KRaft controller: detect missed heartbeats
  3. KRaft controller → broker 2 (ISR): you are leader of orders-0 (new leader epoch)
  4. 📝 broker 2 (ISR): clients refresh metadata → write to broker 2
  5. 📝 broker 1 (leader): returns → truncates to leader epoch → re-syncs as follower

 ┌── Broker local disk (hot) ──┐     ┌──── Object storage (cold) ────┐ │ recent segments, fast reads │ ──▶ │ S3 / GCS / Azure Blob          │ │ local.retention.ms = 1 day  │     │ retention.ms = 1 year, cheap   │ └─────────────────────────────┘     └────────────────────────────────┘   ✔ smaller, cheaper brokers   ✔ faster rebalancing/recovery   ✔ long replay history
