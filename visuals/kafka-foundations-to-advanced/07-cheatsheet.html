🩻 Troubleshooting Flow

👀 Boxes light up as the flow reaches them and each arrow draws in the order the guide defines it. Glowing dots keep running along the arrows to show which way things move.

Step by step

  1. Problem → Symptom?
  2. Symptom? → advertised.listeners reachable? DNS, ports, TLS/SASL config, localhost inside Docker Client can't connect / hangs
  3. Symptom? → More consumers ≤ partitions, faster processing, batch work, more partitions Consumer lag growing
  4. Symptom? → max.poll.interval.ms exceeded? lower max.poll.records, static membership, KIP-848 protocol Rebalance storms
  5. Symptom? → ISR < min.insync.replicas broker down or lagging → check URP NotEnoughReplicas
  6. Symptom? → At-least-once is expected → idempotent consumer / EOS Duplicates
  7. Symptom? → Different keys → different partitions, partitions added later? Out-of-order events
  8. Symptom? → max.request.size / message.max.bytes / max.partition.fetch.bytes, or claim-check RecordTooLarge
  9. Symptom? → Lower retention, tiered storage, check compaction, add brokers Disk full

📋 Golden Rules

 1. RF=3, min.insync.replicas=2, acks=all, idempotence on 2. Choose keys for ordering AND even distribution; size partitions up front 3. One long-lived producer per app; always handle send callbacks 4. Commit offsets AFTER processing; consumers must be idempotent 5. Keep processing between polls short → avoid rebalance storms 6. Retry topics + DLT for poison records 7. Schemas with a registry + compatibility rules 8. Outbox + CDC instead of dual writes 9. TLS + SASL + ACLs, auto.create.topics.enable=false, topics as code10. Alert on URP, under-min-ISR, offline partitions, consumer lag
